Azure Physical Infrastructure
Azure runs from large buildings called 
datacenters
. 
A datacenter contains 
servers, storage, and networking equipment
. 
It also has 
power, cooling, and security
 to keep everything running. 
Microsoft has 
many datacenters around the world
. 
You cannot choose or access a specific datacenter directly. 
Instead, Azure groups datacenters into 
Regions
 and 
Availability Zones
. 
These groups help keep your applications 
available and reliable
, even if one datacenter has a problem. 
🎤 One-Line Summary
"Azure is built on datacenters, and these datacenters are organized into Regions and Availability Zones to provide high availability and reliability."

Fourth
, it helps meet legal, compliance, and regulatory requirements.
One more important point.
A Geography usually contains 
multiple Azure Regions
.
Why?
Because if one Region has a problem, another Region in the same Geography can be used for backup or disaster recovery.

It is also thinking about 
high availability
 and

Now let's move to another important Azure concept.
Availability Zones.
Before I explain it...
Let me ask you a question.
What happens if an entire datacenter loses power?
Maybe there is a fire...
A flood...
Or a major network failure.
If your application is running in only that datacenter...
Your application will also stop working.
So how can Azure protect us from this?
That's where 
Availability Zones
 come in.
First, let's understand what an Availability Zone is.
An 
Availability Zone
 is a 
physically separate datacenter
 inside the same Azure Region.
Notice something important.
We are 
still inside the same Region.
We are 
not moving to another Region.
We are simply using different datacenters within that Region.
Availability Zones



========================================
SLIDE 13
========================================
13 ===
For example...
Suppose you deploy your application in 
Central India
.
Inside that Region, Microsoft may have:
Zone 1 
Zone 2 
Zone 3 
Each zone is a separate datacenter.
Each one has its own:
Power supply 
Cooling system 
Network connection 
So if one datacenter has a major problem...
The other zones continue running.
Let's take a simple example.
Imagine you own an online shopping website.
You create two virtual machines.
VM1 is in Zone 1. 
VM2 is in Zone 2. 
A Load Balancer sends customers to both virtual machines.
Now suppose Zone 1 loses power.
VM1 stops working.
But VM2 in Zone 2 is still running.
Customers can continue shopping without even knowing that one datacenter had a problem.
That is the power of Availability Zones.
Availability Zones

SLIDE 14

14 ===
Now here's an important point.
Availability Zones protect against 
datacenter failures
.
They do 
not
 protect against an entire Region becoming unavailable.
If the whole Region has a problem...
Availability Zones alone cannot help.
For Regional disasters, we use another Azure Region for disaster recovery.
So remember this simple rule.
Availability Zone = Protection from datacenter failure.
Region Pair = Protection from regional failure.
Let's summarize Availability Zones.
They exist inside a single Azure Region. 
Each Zone is a physically separate datacenter. 
Every Zone has independent power, cooling, and networking. 
They protect applications from datacenter failures. 
They improve application availability. 
Availability Zones

Now let's look at another feature that sounds similar...
Availability Sets.
Many beginners confuse

Let me ask you another question.
Imagine your virtual machine is healthy.
The datacenter is also healthy.
But Microsoft needs to install a security update on the physical server hosting your VM.
What happens?
That physical server needs to restart.
If your application has only one VM...
Your application becomes unavailable for a short time.
How can Azure reduce this risk?
That's where

 help.
An

 is a way to place multiple virtual machines on

Notice the difference.

.
Availability Zones use 
multiple datacenters
.
Availability Sets.



========================================
SLIDE 16
========================================
16 ===
Azure automatically spreads your VMs across two important groups.
The first group is called a 
Fault Domain
.
Let's understand that first.
A 
Fault Domain
 is a group of hardware that shares common components like power supply, network switch, or storage.
If one rack or one power unit fails...
Only the VMs in that Fault Domain are affected.
Azure places your VMs in different Fault Domains.
So one hardware failure doesn't stop all your VMs.
Now the second group.
This is called an 
Update Domain
.
Microsoft regularly updates the physical servers.
Instead of restarting every server at the same time...
Azure updates one Update Domain first.
After that finishes...
It moves to the next Update Domain.
This means not all your virtual machines restart together.
Your application can continue serving users.
Availability Sets.



========================================
SLIDE 17
========================================
17 ===
Let's see an example.
Suppose you have two virtual machines.
VM1 is placed in Fault Domain 1 and Update Domain 1.
VM2 is placed in Fault Domain 2 and Update Domain 2.
Now Microsoft performs maintenance.
Only VM1 restarts first.
VM2 keeps running.
After VM1 comes back online...
Azure updates VM2.
Your application remains available throughout the maintenance process.
So Availability Sets protect against two things.
First
, hardware failures using Fault Domains.
Second
, planned maintenance using Update Domains.
Availability Sets.

What is HPC?
HPC stands for 
High Performance Computing
.
Normally, one computer solves one problem.
In HPC, 
hundreds or even thousands of virtual machines work together to solve one very large problem.
Instead of one VM taking 10 days, 1,000 VMs can finish the same job in a few hours.
Real-world example
Imagine a pharmaceutical company.
Scientists are trying to discover a new medicine.
To find the correct molecule, they need to test 
billions of chemical combinations
.
One VM would take months.
So Azure creates thousands of HPC virtual machines.
Each VM tests a small group of molecules.
All the results are combined together.
This dramatically reduces the research time.

What is an Azure Spot VM?
An 
Azure Spot VM
 is an Azure virtual machine that uses 
unused (spare) capacity
 in Microsoft's datacenters. Because Azure can reclaim that capacity at any time, Spot VMs are offered at a 
significantly lower price
 than regular VMs.
Think of it like this:
Azure has many servers. If some are sitting idle, Azure rents them at a big discount. But if another customer needs that capacity, Azure can take the Spot VM back.
How it works
Regular VM
You request a VM
        │
        ▼
Azure creates the VM
        │
        ▼
VM keeps running until you stop or delete it
Spot VM
You request a Spot VM
        │
        ▼
Azure uses spare capacity
        │
        ▼
VM runs normally
        │
        ▼
Azure needs the capacity
        │
        ▼
Spot VM may be evicted (stopped or deleted)
Why is it cheaper?
A regular VM reserves capacity for you.
A Spot VM 
does not reserve capacity
. Azure can reclaim it whenever capacity is needed elsewhere.
That's why Spot VMs can be much cheaper.

"So, don't think of a 
compromised web application
 as a different application. It's the 
same web application
 that was working normally, but an attacker has found a vulnerability, such as SQL Injection or Remote Code Execution, and is now using that application to run malicious commands. Normally, the web application only does its intended job, like displaying products, processing orders, or reading a specific secret from Azure Key Vault using its Managed Identity. But once it's compromised, the attacker may try to access sensitive Azure services like the 
Instance Metadata Service (IMDS)
 to obtain a Managed Identity access token, and then use that token to access other Azure resources such as Key Vault, Storage Accounts, or SQL databases. Azure doesn't simply label an application as 'compromised'; instead, security solutions like Microsoft Defender monitor its behaviour and look for suspicious activities, such as unexpected token requests, unusual network connections, or attempts to access resources the application has never used before. This is where the 
Metadata Security Protocol
 becomes important. It adds an extra security layer in front of IMDS and 
WireServer
 by using the 
Guest Proxy Agent
 and 
eBPF
 to verify that requests are coming from trusted and authorised applications. If an attacker tries to misuse the web application to steal Managed Identity tokens, the request can be blocked before it ever reaches IMDS. In simple words, Metadata Security Protocol helps ensure that even if an attacker manages to compromise a web application, they cannot easily use it as a stepping stone to gain access to the rest of your Azure environment."
